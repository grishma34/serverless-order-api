# Serverless Order API

![coverage](docs/assets/coverage.svg)
&nbsp;`python3.14` · `arm64` Lambda · DynamoDB single-table · AWS SAM

A serverless REST API for customer orders on AWS. Built to demonstrate production
patterns rather than feature count: a single-table DynamoDB design with zero
scans, idempotent writes that survive Lambda retries, one-domain delivery through
CloudFront, and a deploy pipeline with no long-lived credentials.

> **Status — built, tested, deployed, smoke-checked.**
> All seven phases of `PLAN.md` are implemented. 605 tests pass at 100% coverage,
> CI is green on `main`, and the stack is live on AWS: every route below has been
> exercised against real DynamoDB, IAM and CloudFront. The 15-row checklist is in
> [`docs/SMOKE_EVIDENCE.md`](docs/SMOKE_EVIDENCE.md), generated from the actual
> HTTP responses. What remains genuinely unproven is listed under
> [Limits](#limits) — it is the honest boundary of this project, not a footnote.

**Live:** <https://d3i0ojth5tge0.cloudfront.net> — UI and API on one domain
(`serverless-order-api-dev`, `ap-southeast-2`).

## Architecture

```
                        ┌──────────────────────────────────────────────┐
   Browser ───────────► │                 CloudFront                   │
                        │        one domain for UI and API             │
                        └───────┬──────────────────────────┬───────────┘
                        default │                          │ /api/*
                                ▼                          ▼
                     ┌────────────────────┐    ┌───────────────────────┐
                     │  S3 (frontend)     │    │ API Gateway (HTTP API)│
                     │  private, OAC-only │    └──────────┬────────────┘
                     └────────────────────┘               │
                                                          ▼
                                   ┌──────────────────────────────────────┐
                                   │  5 Lambdas (python3.14, arm64)       │
                                   │  create · get · list×2 · update      │
                                   │  one scoped IAM policy each          │
                                   └──────────────────┬───────────────────┘
                                                      ▼
                                   ┌──────────────────────────────────────┐
                                   │  DynamoDB — 1 table, 2 sparse GSIs,  │
                                   │  TTL, no scans                       │
                                   └──────────────────────────────────────┘

   GitHub ── merge to main ──► Actions ── OIDC ──► sam build && sam deploy
```

Because the UI and the API share a CloudFront domain, the browser makes only
same-origin requests — there is no CORS configuration anywhere in this project,
which is a design outcome rather than an omission.

## What it demonstrates, and what proves it

Each claim below names the test that backs it. Captured output for the first
three is in [`docs/EVIDENCE.md`](docs/EVIDENCE.md), regenerated by
`bash docs/evidence/capture.sh`.

| Claim | Proof |
|---|---|
| **No table scans**, ever (REQ-0012) | `tests/unit/data/test_no_scan.py` — a static grep over `src/` *and* a botocore call log of the operations actually issued. A meta-test fires a real `Scan` so the detector can't pass vacuously. Enforced in IAM too: no function policy grants `dynamodb:Scan`. |
| **A retry cannot create a duplicate** (REQ-0010) | `TestIdempotentCreate` + `TestReplaySemantics` — one `TransactWriteItems` with condition expressions on both the idempotency record and the order. The second create raises, leaves exactly one order, and writes no rows at all. |
| **Indexes can't disagree with the item** (REQ-0011) | `transition_status` rewrites `status`, `GSI1SK` and `GSI2PK` in one conditional `UpdateItem` pinned to the expected current status. |
| **6 documented access patterns, all `Query`/`GetItem`** | One test per pattern in `test_order_repository.py`; every query maps to a row in `docs/DYNAMODB_DESIGN.md`. |
| **Complete state machine** (REQ-0006/0007) | All 25 ordered status pairs asserted, plus reachability and acyclicity — not a sample. |
| **Infrastructure is checked, not just linted** | `tests/unit/infra/` asserts the template matches the design doc, no policy grants `Scan` or uses a `*` resource, no workflow reads a static AWS key, and the OIDC trust is pinned to one repo and branch. |
| **The frontend can't drift from the server** | A test parses the UI's transition map out of `app.js` and compares it to `services/status_machine.py`. Another fails the build if an absolute API origin ever appears in `frontend/`. |

## Test suite

605 tests, 100% coverage of `src/` (596 statements, 122 branches), gate at 90%.
No test touches AWS: an autouse fixture plants unusable credentials so an escaped
mock fails on authentication rather than reaching a real account (NFR-0002).

| Layer | Tests | AWS |
|---|---|---|
| `tests/unit/shared/` | 51 | none |
| `tests/unit/data/` | 71 | moto |
| `tests/unit/services/` | 232 | none — in-memory fake repository |
| `tests/unit/handlers/` | 108 | moto, end-to-end through the real stack |
| `tests/unit/infra/` | 143 | none — templates, workflows and docs read as data |

The service layer runs against a fake repository, which is only sound while the
fake fails the same way the real one does — so `test_fake_matches_repository.py`
runs the same scenarios against both the fake and moto.

## Running it

```bash
python3.14 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt   # pulls in src/requirements.txt too

# The quality gate — what CI runs
ruff check src tests && ruff format --check src tests
pytest --cov=src --cov-report=term-missing --cov-fail-under=90

# Infrastructure
sam validate --lint
sam build          # needs the venv active: system python3.14 has no pip
```

```bash
# Deploy a stack of your own, then prove it works
sam deploy --config-env dev
bash docs/evidence/smoke.sh <site-url> <frontend-bucket> <region> <stack-name>
```

## API

Base path `/api`, routed by CloudFront to API Gateway. Full detail in
[`docs/API_SPEC.md`](docs/API_SPEC.md).

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/orders` | Create — `Idempotency-Key` required; `201`, or `200` on replay |
| `GET` | `/api/orders/{orderId}` | Fetch one order with its line items |
| `GET` | `/api/customers/{customerId}/orders` | A customer's orders; `?status=` filters |
| `GET` | `/api/orders?status=X` | Ops listing across customers |
| `PATCH` | `/api/orders/{orderId}` | Status transition; `409` if illegal |

```
PLACED ──► PAID ──► SHIPPED ──► DELIVERED
   │         │
   └────┬────┘
        ▼
    CANCELLED          (terminal; DELIVERED also terminal)
```

## What the deployment settled

Three things could not be proven locally at all, because the local stand-ins are
imitations rather than the thing itself. `PLAN.md` § Risks named all three; the
deployment closed all three. Captured responses:
[`docs/SMOKE_EVIDENCE.md`](docs/SMOKE_EVIDENCE.md), regenerable with
`bash docs/evidence/smoke.sh`.

| Open question | Settled by | Result |
|---|---|---|
| **moto vs real DynamoDB.** `TransactWriteItems` condition semantics are the mechanism behind REQ-0010, and moto imitates them rather than being them. | Two POSTs sharing one `Idempotency-Key`, through CloudFront | `201` then `200`, byte-identical body, customer still has exactly one order |
| **GSI-only IAM scoping.** The two list functions hold `dynamodb:Query` on their index ARN and *not* on the table, so they cannot read the base table. Sufficient for an index `Query`? | Both listing routes against the live stack | `200` — the index ARN alone authorises the `Query`, and the tighter scope stands |
| **CloudFront path handling.** Routes carry the `/api` prefix and the stage is `$default`, so `/api/*` should arrive unrewritten — and `Idempotency-Key` must survive the hop. | Running the entire checklist against the CloudFront domain, never the API Gateway endpoint | Every route reached its Lambda; the header survived, which is what row 2 depends on |

The bucket refuses a direct object request with `403`, so CloudFront with OAC is
the only path to the frontend (REQ-0020) — the other half of the same test.

The frontend mints an idempotency key per submission and **reuses it when a
submission fails**, so the replay check also runs straight from the UI via the
"Resend with the same key" button.

## Limits

Deliberate boundaries, not oversights:

- **One environment is a demo, not a fleet.** The stack is deployed to a single
  region with no custom domain, no WAF and no alarms. `PriceClass_100` keeps the
  CDN cheap rather than global.
- **No authentication.** Any caller can create and transition any order. Cognito
  is listed under future work below, and adding it would change the API surface.
- **Load is untested.** On-demand DynamoDB and Lambda concurrency should absorb
  a demo's traffic, but nothing here has been benchmarked, so the NFR-0006 cost
  claim is an argument from the pricing model rather than an observation.
- **The deploy role is broad by design.** `bootstrap/github-oidc.yaml` documents
  why several statements are service-scoped, and what to harden first if this
  ever guarded something valuable.

`TASKS.md` carries the same boundaries against the individual checkboxes.
